# xmind 测试用例 -> weknora 知识库归档

## 概述

四个测试专家都会产出 xmind 格式的测试用例。本 skill 负责把**终稿 xmind** 转成 Markdown，按预置映射自动匹配「业务线 → 空间 → 知识库」，与测试人员确认后上传到团队 weknora，同时在专家流程的每个必做步骤收尾时检查是否已同步并提醒。

核心原则：

- **测试人员零配置**：测试人员**唯一要做的事**是在 AI 工具里配好 MCP 连接器（只填 `url` 与 `Authorization`）。除此之外**不生成、不维护任何本地 json**——不要要求测试人员创建或修改 `weknora_mcp.json`。
- **映射表内置**：空间、知识库名/ID、业务线、对应专家全部预置在 `assets/preset_kb_mapping.json`，随 skill 分发。**测试人员无需配置映射**，开箱即可自动匹配。
- **映射的维护方是智能体**：后续新增知识库由智能体发现、与测试人员确认归属后写回内置预设（`--add-kb` / `--sync-kb`，默认 `--target preset`），随 skill 升级分发到全团队。本地覆盖配置（`--target local`）仅供排障，不是给测试人员的操作。
- **连接器只认 url + Authorization**：weknora 空间身份以 **weknora 空间ID + 空间名称** 为准，连接凭据是 MCP 的 `url` 与 `Authorization`。MCP 服务器名由各人在连接器中**自定义**，不是固定值，脚本按 `mcp_url` 自动识别（`init_config.py --discover`）。
- **上传内容只能是 Markdown**（weknora `add_document` 接受 `content` 文本或 `url`，不接受 .xmind/.xlsx 二进制）。
- **上传前必须确认**：每次上传前展示确认卡，逐项核对业务线、空间、知识库（含空间ID与知识库ID）、专家归属，得到明确答复后才上传。
- 未上传时只提醒、**不阻塞**流程推进。

## 上传前强制确认（所有模式通用，硬性）

**没有拿到测试人员的明确确认，绝不执行上传**（单条、批量都一样）。沉默、答非所问、或只说"嗯/好"而未针对确认卡答复，均视为未确认。

确认卡必须完整展示以下 8 项（业务线 + 空间ID + 空间名称 + 知识库名/ID + 专家 + **weknora 标签** 是防错重点）：

```
请确认本次上传目标（回复「确认」后我才上传）：
1. 业务线：效贷（XD）｜对应专家：效贷效融测试专家-轻量版
2. 空间：场景业务线（weknora 空间ID 10004）
3. 知识库：效贷_测试_测试用例（ID 6603ca32-0432-424e-8972-628377d4bfe0）
4. 文档类型：测试用例（weknora 标签：测试用例）
5. 文档标题：效贷_PRJ-00770309_额度申请_测试用例_20261015
6. 来源文件：D:\…\额度申请_测试用例_终版.xmind（共 1 份 / 批量时写总数）
7. 上传方式：新建 / 更新已有文档（<doc_id>）
8. weknora 标签：需上传后人工勾选（当前通道限制，见「weknora 标签」章节）
```

规则：

- **每次上传前都要确认**，不能因为上一次确认过就跳过；批量模式至少在整批开始上传前确认一次。
- 出现下列任一情况，**必须重新确认**：业务线/产品/文档类型/知识库任一变化；命中多个候选；换了一批文件；测试人员中途更正过一次信息。
- 测试人员说「不是这个库 / 应该是 XX 库」时：先改目标（必要时登记映射）再重新展示确认卡，不得在原目标上继续上传。
- 知识库名称与 ID 必须**逐字核对**，不凭印象匹配。
- 若路由命中的是**未登记/新增知识库**，先按下一节处理，不得直接上传。

## 指定目标与预设不一致时（必须停下来问，禁止猜测）

测试人员口述/指定的**知识库、空间、业务线**与预设映射对不上时，不要按相似名称凑一个目标，也不要默认用路由结果硬传。按下面做：

**第一步：把差异说清楚**（脚本会输出，见 U4 的退出码 3/4），例如：

```
指定空间「智慧记」= 10006，但预设中「效贷_测试_测试用例」属于 场景业务线（10004）
```

**第二步：主动询问是否有新知识库**（必须原样传达下面的话术要点）：

> 你指定的目标与团队预设映射不一致 —— 是 weknora 里新建了知识库，还是换了一条业务线/空间？
>
> 如果是新建了知识库，**你只需告诉我一句：「新增了 XX 库，归属 效贷 / 效融 / 泾渭云 / 小贷 / 智慧记零售 / AI进销存」**。我会与你确认归属后写进 skill 内置映射，随下次升级分发给全团队，**不需要你自己配置任何 json**。

**第三步：按答复处理**

| 答复 | 处理 |
| --- | --- |
| 「是新建了 XX 库，归属 XX 线」 | `--diff-kb` 对账 → `--add-kb` 登记 → `--validate` + `resolve_target` 复核 → 展示确认卡 → 上传 |
| 「是我记错了，应该是 XX」 | 用更正后的目标重跑路由 → 展示确认卡 → 上传 |
| 未答复 / 答非所问 | 视为未确认，**不上传**，本轮最多只完成「转 MD 落盘」 |

**第四步：登记后记得重新打包 skill 分发**，团队其他机器才能拿到新映射。

> 补充：即使测试人员没指定、路由自动命中的情况下，若会话中出现"我平时都传到 XX 库"这类与预设不符的说法，同样按本流程先确认。

## 未登记 / 失效知识库的发现与确认

每次会话首次上传前（或怀疑映射过期时），用 MCP 拉一次知识库清单并与映射对账：

1. `{mcp_prefix}list_knowledge_bases` → 结果存成 `kb_list.json`
2. `python scripts/init_config.py --diff-kb --space <空间ID> --from-json kb_list.json`

- **发现未登记知识库**（weknora 有、映射没有）：必须列出并询问测试人员——「发现 N 个映射里没有的知识库：… 本次要传的是哪个？归属哪条业务线？」未登记库**不得**直接作为上传目标；确认后用 `--add-kb` / `--sync-kb` 登记并 `resolve_target` 复核通过再上传。
- **发现失效项**（映射有、weknora 没有，可能改名或删除）：提醒人工核实，不静默沿用旧名称。
- 路由脚本返回退出码 3（未命中）时：同样按本流程处理，**禁止凭相似名称猜测**。

## weknora 标签（区分文档类型）

weknora 知识库页面支持按**标签**筛选文档，团队用 `测试用例` / `测试总结` / `测试需求分析` / `测试缺陷` 四个标签区分文档类型。标签是**知识库级**的——每个知识库各有一套自己的标签。

**文档类型由本 skill 自动判定**（来源：专家身份 + 会话上下文 → 标题模板 + MD 头部元信息 + 确认卡第 4 项），标签名 = 文档类型，映射见预设 `tags.map`（`resolve_target.py` 输出的 `tag` 字段）。

### 当前限制（实测结论，务必如实告知测试人员）

| 项 | 现状 | 依据 |
| --- | --- | --- |
| 自动判定文档类型 | ✅ 可以 | `resolve_target.py` 的 `doc_type` / `tag` 输出 |
| 通过 MCP 自动打标签 | ❌ 不行 | weknora MCP 服务端 `tools/list` 仅注册 10 个工具（add_document / update_document / list_documents / read_document / list_knowledge_bases / search_knowledge / grep_chunks / wiki_index / wiki_read_page / wiki_search），**均无标签参数**；`add_document` 的 schema 只有 knowledge_base_id / title / content / url / publish |
| 通过 weknora REST 打标签 | ⚠️ 服务端支持，但需换鉴权 | REST 有 `/api/v1/knowledge-bases/{kb}/tags`（标签增删改查）与 `/api/v1/knowledge/tags`（文档打标），前端上传确认框本身就有「标签」页签；但 MCP 令牌（`mcp_xxx`）对 `/api/*` 返回 **401**（实测） |

### 当前生效方式：方案 C（人工勾选 + 全程提醒追踪）

**已选定方案 C**：文档类型由 skill 自动判定（写进标题、MD 头部、确认卡），标签由测试人员在网页端勾选；skill 负责**每次都提醒、记录进度、步骤收尾复查**，确保不漏标、不标错。

智能体必须做到的四件事：

1. **判定并告知**：`resolve_target.py` 输出的 `tag` 字段即标签名，确认卡第 8 项与每条回执都要带上。
2. **上传后提醒**：给出精确操作路径——
   > weknora 知识库页（**效贷_测试_测试用例**，空间：场景业务线）→ 勾选刚上传的文档 → 点「标签」→ 添加标签 → 选择「**测试用例**」→ 确定
3. **记录进度**：上传成功即记 `tag_status=pending`；测试人员打完标确认后回写 `done`。
4. **收尾复查**：每个必做步骤收尾 `sync_state.py check`，输出的 `tag_reminder` / `untagged_total` 非空时要提醒；批量模式在 B6 报告汇总待打标清单。

命令：

```
# 上传成功时带上标签名
python scripts/sync_state.py mark --key "PRJ-00770309|测试用例" --status uploaded \
       --kb "效贷_测试_测试用例" --title "<标题>" --doc-id "<id>" --tag "测试用例"

# 测试人员打完标后回写
python scripts/sync_state.py mark --key "PRJ-00770309|测试用例" --tag-status done

# 看还有哪些没打标
python scripts/sync_state.py list --untagged
```

批量模式同理（`batch_cases.py mark --id 2,3 --tag-status done`），`report` 会按标签分组输出可勾选的清单。

### 前提：四个标准标签要先在各知识库建好

标签是**知识库级**的，8 个测试知识库各要先有这 4 个标签（`测试用例` / `测试总结` / `测试需求分析` / `测试缺陷`）。首次使用前请管理员或测试人员建一次，之后长期复用：

| 空间（空间ID） | 需要建标准标签的知识库 |
| --- | --- |
| 场景业务线（10004） | 效贷_测试_测试用例、效融_测试_测试用例、效贷_测试_测试总结、效融_测试_测试总结 |
| 数据业务线（10003） | 泾渭云_测试_测试用例、小贷_测试_测试用例 |
| 智慧记（10006） | AI零售_测试_测试用例、AI进销存_测试_测试用例 |

建法：知识库页 → 标签 → 新建标签（名称逐字一致，中文无空格）。已建好的库跳过。

### 未来若打通自动打标

- **方案 A（推荐，根因修复）**：请 weknora MCP 维护方加标签能力——底层 REST 已支持，改动小：`add_document` 增加可选参数 `tags: string[]`；新增 `list_tags(knowledge_base_id)`、`set_document_tags(knowledge_id, tags)`。改完后把预设 `tags.auto_assign` 置 `true`、`channel` 置 `mcp`，skill 流程无需改动即自动打标。
- **方案 B（需令牌）**：用 `scripts/tag_documents.py` 走 REST 直连，需**用户登录态令牌**或管理员 API Key（`/api/v1/system/admin/api-keys`）——**MCP 令牌无效**（实测 401）。脚本默认 dry-run，`--check` 自检通道。启用后可批量补建标签（`--ensure-tags`）并给历史文档补标。

方案 A/B 就绪后，本节「前提」的初始化工作可由 `tag_documents.py --ensure-tags --apply` 一次完成。

## 何时使用

- 专家流程中生成 xmind 用例后（提醒模式）。
- 用户说「上传知识库」「同步 weknora」「归档用例」「用例入库」「上传到知识库了吗」。
- 专家任一必做步骤收尾时的同步状态检查。
- 用户要求把**本地某个目录下的历史 xmind 用例批量补录**到某个知识库（批量模式）。

## 三种工作模式

### 模式 R：提醒模式（默认、轻量）

1. 检测到本轮产出/更新了 xmind 用例后，向测试人员提问一次：
   > 已生成 xmind 用例，是否现在上传到 weknora？（目标：场景业务线 / 效贷_测试_测试用例）
2. 回答「是」 -> 进入模式 U。
3. 回答「否」或暂不上传 -> 用 `sync_state.py mark --status pending` 记录，并说明：终版确定后说「上传知识库」即可一键归档。
4. 此后每个必做步骤收尾执行 `sync_state.py check`；未上传则输出一条简短提醒。

### 模式 U：执行模式（七步）

| 步骤 | 动作 | 主要工具/脚本 |
| --- | --- | --- |
| U1 | 收集上下文（业务线、产品、需求、用户故事、文档类型） | 会话上下文 + 必要时一次性询问 |
| U2 | 定位 xmind 终稿 | Glob `**/*.xmind` / 用户指定路径 |
| U3 | 转 Markdown | `scripts/xmind_to_md.py` |
| U4 | 自动匹配空间与知识库 | `scripts/resolve_target.py` |
| U5 | 查重 | `{mcp_prefix}list_documents` |
| U6 | 确认并上传（**必须过「上传前强制确认」**） | `{mcp_prefix}add_document` / `update_document` |
| U7 | 记录状态并回执（回执必带标签名与勾选提醒） | `scripts/sync_state.py mark --status uploaded --tag "<标签>"` |
| U8 | 提醒并追踪打标（方案 C）；测试人员确认打完后回写 | `scripts/sync_state.py mark --tag-status done` |

### 模式 B：批量模式（历史用例补录）

适用于把本地某个目录下的历史 xmind 用例批量转 MD 并上传到指定知识库。**必须先确认业务线、产品、目标知识库，再动手。**

| 步骤 | 动作 | 命令 |
| --- | --- | --- |
| B0 | 检查该空间是否有未登记/失效知识库 | `{mcp_prefix}list_knowledge_bases` + `init_config.py --diff-kb` |
| B1 | 确认四要素：目录、业务线、产品、文档类型（+ 是否递归/是否含 md） | 向用户确认，不要用推断值直接开工 |
| B2 | 扫描生成清单，自动匹配知识库，打印预览与跨线告警（未匹配时按「指定目标与预设不一致」先问是否有新库） | `batch_cases.py scan --dir <目录> --biz-line XD --product 效贷 --out manifest.json` |
| B3 | 展示「上传前强制确认」卡 + 清单（标题、跨线告警项、数量） | 等确认后才继续 |
| B4 | 批量转 MD | `batch_cases.py convert --manifest manifest.json` |
| B5 | 逐条上传（MCP）+ 逐条标记进度（`tag_status` 自动置 `pending`） | `{mcp_prefix}add_document` + `batch_cases.py mark --id N --status uploaded --doc-id <id>` |
| B6 | 输出报告（含按标签分组的待打标勾选清单） | `batch_cases.py report --manifest manifest.json --out 批量上传报告.md` |
| B7 | 测试人员在网页端打完标后回写进度 | `batch_cases.py mark --id 2,3 --tag-status done` |

批量模式同样执行**方案 C**：B5 后必须提醒人工勾选标签，B6 报告给出可勾选清单，B7 回写进度。
批量场景下标签名整批一致（= 文档类型），网页端可一次勾选多份文档再打标，效率较高。

批量模式硬性规则：

- **先确认后执行**：B1 的四要素与 B3 的确认卡必须由测试人员明确确认；`scan` 只生成清单、不上传、不改映射。
- **每批都要确认**：即使上一批已确认过，换目录/换业务线/换文档类型都必须重新走 B1+B3。
- **跨线告警必处理**：文件名里出现其他业务线关键词（如选了效贷却出现「效融」）时，清单会打 `⚠️` 并给出「可能应传到 XX 库」的建议，**必须逐条与用户确认归属**，不得按目录默认值直接上传。
- **清单可人工改**：`manifest.json` 的 `items[].title` / `user_story` / `requirement` 允许人工编辑后再 convert，脚本尊重已改值。
- **逐条上传、逐条记录**：每成功一条立即 `mark`；中断后可用 `convert`(跳过已完成) + 未上传条目续传，不会重复上传已成功项。
- **查重**：批量场景同样按标题查重（`list_documents` + 关键字），已存在则询问更新或跳过，并在清单里标记 `skipped`。
- **失败不中断**：单条失败标记 `failed` 并记录原因，继续下一条，最后在报告中汇总。
- **打标不可省**：批量上传量大、最容易漏标。B6 报告里的勾选清单必须交给测试人员，并追到 B7 回写完成为止。

## Step 0：就绪检查（每次进入先做）

> **测试人员只需配 MCP 连接器（url + Authorization）**。本节全部是"检查"，不是"让测试人员去配置什么"。不要在流程里要求测试人员生成或修改 json。

### 0.1 映射就绪（开箱即用，无需配置）

```
python scripts/init_config.py --list
```

正常情况下直接输出 3 个空间 / 8 条知识库（见上方「团队标准映射」）。数据来源标注为 `preset`（内置预设）时属正常，**不要要求测试人员去配 json**。仅当输出 `preset 缺失`（skill 包不完整）时才需重新解压安装。

### 0.2 连接器识别（这里才是首次使用要引导的地方）

```
python scripts/init_config.py --discover
```

按 `mcp_url` 把本机已配置的 MCP 服务器识别到对应空间，输出每个空间的**服务器名与工具前缀**：

- 三个空间都 ✅ -> 直接用输出的 `mcp_prefix` 调工具。
- 某空间 ❌ -> 说明本机没配该空间的连接器，按「首次使用引导」提醒测试人员。
- 某空间识别到多个条目 -> 询问用哪一个，不要默认取第一个。
- 出现「无法与预设空间对应」的 weknora 类服务器 -> 提示可能连的是测试环境或空间已改名，需人工确认，**不得**用它当上传目标。

### 0.3 MCP 连通性

调用 `{mcp_prefix}list_knowledge_bases`；工具不存在时先在会话中按需加载该 MCP 工具后再调用。不可用 -> 回到「首次使用引导」，本次只完成到 U3（转 MD 落盘）。

### 首次使用（连接器未配置时：必须主动提醒并停下引导）

判定信号：`--discover` 显示目标空间 ❌，或找不到形如 `mcp__<服务器名>__*` 的 weknora MCP 工具。

此时**不要尝试上传**，主动给出 `references/first_use_checklist.md` 的完整清单，重点是三件事：

1. **在连接器里新增该空间的 MCP**，只填两个关键字段：
   - `url`：与 `--discover` 输出的「权威标识 url」**完全一致**（`https://finwiki.kingdee.com/mcp/<空间端点UUID>`）
   - `headers.Authorization`：`Bearer <令牌>`（向团队管理员索取）
   - **服务器名随便起**（如 `weknora-changjingyewu`），技能靠 url 识别，不依赖名字。
2. **点「信任」并重启会话**（WorkBuddy：连接器管理页；其他工具：按其 MCP 配置方式）。
3. **回来验证**：`--discover` 看该空间是否 ✅；再 `{mcp_prefix}list_knowledge_bases` 确认连通。

配置未完成时，最多只做「转 MD 落盘」，绝不上传。不要只丢一句"请先配置"。

## 知识库扩展（后续新增类型如何接入）

知识库名约定为 `<前缀>_测试_<文档类型>`（如 `AI零售_测试_测试缺陷`、`AI进销存_测试_测试需求分析`）。

**这件事由智能体完成，不需要测试人员做任何配置。** 流程：发现（`--diff-kb`）→ 与测试人员确认归属（业务线/产品/专家）→ 写回内置预设 → 复核。

```
python scripts/init_config.py --add-kb  --space 10006 --name "AI零售_测试_测试缺陷" --id <新ID>
python scripts/init_config.py --sync-kb --space 10006 --from-json kb_list.json   # 用 MCP 输出批量补齐，自动跳过已有
```

- 默认写入 **`assets/preset_kb_mapping.json`（团队标准映射）**，随 skill 升级分发到全团队，各台机器开箱生效。
- `--target local` 只在排障时临时用（写本地覆盖配置），**不要让测试人员走这条路**，也不要把本地副本当长期配置——它会盖住 skill 升级后的预设。
- 新增条目会自动继承同前缀知识库的业务线/产品/别名/专家；`doc_type` 由名称推导，缺的用 `--add-kb --biz-line/--product/--doc-type` 补。

配完必须复核：`init_config.py --validate` + `resolve_target.py --biz-line ZHJLS --doc-type 测试缺陷`。**未登记的知识库不会被路由命中**（退出码 3），此时不要自行猜测目标库。

> 提醒：智能体更新过内置预设后，记得重新打包 skill 分发（`package_skill.py`），团队才能拿到新映射。

## U1 收集上下文

从会话上下文（专家身份、用户故事号、需求名、产物路径）推断：

- 业务线：`XD` 效贷、`XR` 效融、`JWY` 泾渭云、`XDK` 小贷、`ZHJLS` 智慧记零售、`AIJXC` 智慧记星火（AI进销存）
- 文档类型：`测试用例`（默认）；`测试总结`、`测试缺陷`、`测试需求分析` 等以映射中实际登记的知识库为准
- 需求名称、用户故事号（如 `PRJ-00770309`）

推断依据不足时，**一次性**问清这四项，不要分多轮。

## U2 定位 xmind 终稿

- 用 Glob 搜索 `**/*.xmind`，按修改时间取最新；多个候选时列出让用户选。
- 确认是否为终稿：文件名含 `终版/终稿/final`，或由测试人员明确确认。**未确认终稿时提示一句**「当前是否为终版？非终版上传后需再次更新」。
- 若输入已是 `.md/.markdown`，直接进入 U4（脚本支持透传）。

## U3 转换 Markdown

```
python scripts/xmind_to_md.py <用例文件.xmind> -o <输出.md> --meta 业务线=效贷 --meta 产品=效贷 \
       --meta 用户故事=PRJ-00770309 --meta 需求=额度申请 --meta "weknora标签=测试用例"
```

- 支持新版 `content.json` 与旧版 `content.xml`；`.md` 输入直接透传并补元信息头。
- `weknora标签` 元信息会写进 MD 头部，测试人员在知识库里打开文档就能看到该打哪个标签（批量 convert 自动带上）。
- 层级错乱时改用 `--style heading`。
- 输出后**回显前 30 行**给测试人员确认结构正确。

## U4 自动匹配空间与知识库

```
python scripts/resolve_target.py --biz-line XD --doc-type 测试用例 --user-story PRJ-00770309 --requirement 额度申请 --mcp-prefix <discover得到的工具前缀>
```

测试人员明确说了目标空间/知识库时，把它们一起传进去做一致性校验（**这一步能挡住"传错库"**）：

```
python scripts/resolve_target.py --biz-line XD --space 10004 --kb "效贷_测试_测试用例" --user-story PRJ-00770309 --requirement 额度申请
```

- 退出码 0：输出 `space_id / space_name / biz_line_name / kb_name / kb_id / expert / title`。
- 退出码 2（多候选）：**列出候选让测试人员选择**，或用 `--kb "知识库名称"` 指定。
- 退出码 3（未命中/未登记）：按「指定目标与预设不一致时」+「未登记 / 失效知识库的发现与确认」处理——**禁止凭相似名称猜测**，先问是否有新知识库，确认归属并登记后再重试。
- 退出码 4（命中但与你指定的空间/业务线冲突）：同样按「指定目标与预设不一致时」处理，输出会写明"指定空间 X 与预设中该库所属 Y 不一致"。

## U5 查重

调用 `{mcp_prefix}list_documents`，参数 `knowledge_base_id` 填 `kb_ref`（id 或精确名称），`keyword` 填用户故事号或需求关键字。

- 命中已有文档 -> 询问「更新已有 / 新建一份」，默认建议更新（避免知识库里堆积多份版本不明的用例）。
- 未命中 -> 新建。

## U6 确认并上传

必须按「上传前强制确认」展示确认卡，得到明确肯定答复后再执行（未确认不得上传）：

```
请确认本次上传目标（回复「确认」后我才上传）：
1. 业务线：效贷（XD）｜对应专家：效贷效融测试专家-轻量版
2. 空间：场景业务线（weknora 空间ID 10004）
3. 知识库：效贷_测试_测试用例（ID 6603ca32-0432-424e-8972-628377d4bfe0）
4. 文档类型：测试用例（weknora 标签：测试用例）
5. 文档标题：效贷_PRJ-00770309_额度申请_测试用例_20261015
6. 来源文件：<MD 路径 / xmind 路径>，共 N 行
7. 上传方式：新建 / 更新已有文档（<doc_id>）
8. weknora 标签：上传后需人工勾选（方案 C，回执会再提醒一次）
```

新建：

```
{mcp_prefix}add_document
  knowledge_base_id: <kb_ref>
  title: <标题>
  content: <Markdown 全文>
  publish: true
```

更新已有：

```
{mcp_prefix}update_document
  knowledge_id: <文档 id>
  content: <Markdown 全文>
  title: <标题，可省略沿用旧标题>
```

## U7 记录状态与回执

```
python scripts/sync_state.py mark --key "PRJ-00770309|测试用例" --status uploaded --biz-line XD \
       --kb "效贷_测试_测试用例" --title "<标题>" --doc-id "<返回id>" \
       --md-path "<MD 路径>" --xmind-path "<xmind 路径>" --tag "测试用例"
```

回执内容（**标签相关为必填项**）：

```
✅ 已上传
空间：场景业务线（10004）
知识库：效贷_测试_测试用例
标题：效贷_PRJ-00770309_额度申请_测试用例_20261015
文档ID：<id>

⚠️  还需一步：请到 weknora 给该文档打上标签「测试用例」
    知识库页 → 勾选该文档 → 标签 → 添加标签 → 选择「测试用例」→ 确定
    打完请回复「已打标签」，我回写进度。
```

失败时保留本地 MD 并提示重试方式。

## U8 提醒并追踪打标（方案 C）

- 上传成功后**立即**在回执里给出上节的标签勾选路径，不要等测试人员问。
- 测试人员回复「已打标签 / 打好了」→ `sync_state.py mark --key "<键>" --tag-status done`，并回复确认。
- 未回复、或回复不确定 → 保持 `pending`，在后续步骤收尾继续提醒（不阻塞流程）。
- 流程最后一个必做步骤结束时仍未打标 → 提醒语气加强为「文档已入库但未打标签，将影响按文档类型筛选」。

## 提醒规则（专家合并后生效）

- `sync_state.py check --key "<用户故事>|<文档类型>"`
  - 0（已上传）：**还要看 `tag_reminder` 与 `untagged_total`**——非空即提醒人工打标；已打标则静默。
  - 10/12（pending/无记录）：输出一条提醒，含目标知识库名与触发语「说『上传知识库』即可归档」。
  - 11（skipped）：仅提醒一次，不再追问。
- `sync_state.py list --untagged` 可随时列出全部「已上传但未打标」的文档。
- 提醒不阻塞后续步骤；但流程最后一个必做步骤结束时，提醒语气加强为「终版用例未入库 / 入库但未打标签」。

## 命名与查重规范

- 标题模板取自映射的 `naming.title_template`（默认 `{product}_{user_story}_{requirement}_测试用例_{yyyyMMdd}`）。
- 同一需求重复上传：默认更新已有文档；确需并存时在标题尾部追加 `_v2` 或时间戳。
- 元信息（业务线/产品/用户故事/需求/生成日期/来源文件）写入 MD 头部，便于在知识库中回溯到原始 xmind。

## 边界与限制

- 只能上传 Markdown；.xmind/.xlsx 原文件保留在本地或共享盘，不进知识库。
- **标签走方案 C（人工勾选 + 全程提醒追踪）**：MCP 无标签参数（`add_document` schema 无 tags），REST 有但需另配令牌。文档类型仍会**自动判定**并写进标题、MD 头部与确认卡；标签由测试人员在网页端勾选，skill 用 `tag_status` 追踪进度并在每个步骤收尾复查。`tags.auto_assign` 为 `true` 时（MCP 或令牌就绪后）自动打标。
- 三个空间（10004 场景业务线 / 10003 数据业务线 / 10006 智慧记）的 8 个测试知识库均已登记映射并已在本机连通；若某台机器缺某个空间的连接器，该业务线只走到 U3 并提示配置。
- **测试人员的工作只有一项**：在连接器里配 `url` + `Authorization`。不生成 json、不改映射、不填知识库 ID。
- 令牌与 MCP 授权属于团队凭据：不写进 skill、不提交 Git、不在会话中明文回显。`assets/preset_kb_mapping.json` 只含空间 url（无令牌）。
