# 需求评审 Prompt

用于用户明确要求“评审需求/评审技术方案”时执行。默认不参与普通需求整理流程。

## 触发条件

仅当用户明确说：

- “评审这个需求”
- “做需求评审”
- “评审技术方案”
- “看看有哪些问题/风险”

## 默认输入

- 已确认需求整理稿，或用户指定的需求/技术方案文档。
- 技术方案如用户提供或同目录明显存在，可读取用于一致性检查。
- 默认不读取知识库、不做历史对比。

## 知识库触发

只有用户说“结合历史”“参考知识库”“对比历史”“同类需求”时，才读取相关历史材料。

## 评审维度

| 维度 | 检查内容 |
|------|----------|
| 需求疑问 | 业务逻辑不清、条件缺失、状态不完整 |
| 模糊点 | 时间、范围、枚举、成功/失败口径不明确 |
| 完整性 | 背景、目标、影响范围、异常分支、回归范围 |
| 可测试性 | 是否有明确输入、动作、预期、验证方式 |
| 需求-技术一致性 | 技术方案是否覆盖需求，字段/状态/接口是否一致 |
| 技术风险 | 第三方依赖、超时、幂等、数据一致性、安全合规 |

## 输出格式

```markdown
# 需求评审结果

## 评审概览
| 严重 | 重要 | 一般 |
|------|------|------|
| N | N | N |

## 严重问题
### 1. 问题标题
- 位置：...
- 问题：...
- 影响：...
- 建议：...

## 重要问题
...

## 一般问题
...

## 待确认问题
| 序号 | 问题 | 建议确认人/方向 |
|------|------|----------------|
```

## 可选文件输出

> **文件名前缀规则**：本环节（步骤② 需求评审）产出的文件必须以所属环节步骤编号 `2-` 作为前缀。

用户明确要求生成文件时，再输出：

- `2-{需求名}_评审报告.md`
- `2-{需求名}_评审数据.json`

## 禁止项

- 普通“整理一下”不触发评审。
- 默认不读取知识库。
- 不评审过细运维方案，如日志存储策略、告警渠道、灰度细节。
- 不把建议当成已确认需求。
