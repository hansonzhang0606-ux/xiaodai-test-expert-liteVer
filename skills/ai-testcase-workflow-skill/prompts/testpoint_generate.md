# 测试点与 XMind 生成 Prompt

用于在用户确认需求整理完成后，生成测试点 JSON 和 XMind。

## 触发条件

仅当用户明确说以下任一表述时执行：

- “文档完成”
- “确认整理完成”
- “开始生成测试点”
- “生成测试点”
- “生成 XMind”

如果用户仍在补充需求、页面信息或规则，不执行本阶段。

## 默认输入

优先使用已确认的需求整理稿。可补充读取：

- 用户明确指定的需求文档
- 同目录 `*整理版*.md`
- 用户在对话中补充的页面/接口/规则信息
- 技术方案文档（如用户提供或同目录明显存在）

默认不读取知识库、不读取历史需求、不读取精华库。

## 默认流程

1. 读取已确认需求稿。
2. 提取需求功能点、业务场景、影响对象、入口、规则、判断条件、边界条件、异常分支。
3. 先在对话中输出测试点结构预览，方便用户快速确认。
4. 用户无异议或明确要求生成文件时，生成测试点 JSON。
5. 调用 `scripts/generate_xmind.py` 由 JSON 生成 XMind。
6. 输出文件路径和测试点数量统计。

## 结构原则

默认按 3-4 层组织，宁可少而准，不要为了完整模板硬凑模块。

测试点结构优先贴近人工维护习惯：先按“需求功能点/业务场景/影响对象”拆一级节点；复杂功能点允许继续拆子功能点/子场景，直到能自然挂具体测试点为止；再在具体功能点下覆盖正常流程、业务规则、边界组合、异常场景。

不要把“功能流程、业务规则、边界与组合场景、异常场景”固定作为全局一级大模块。它们只是测试设计维度，用来检查每个功能点是否覆盖完整。

### 推荐分层

| 层级 | 拆分依据 | 示例 |
|------|----------|------|
| 一级节点 | 需求功能点、业务场景、影响对象 | 测额结果流水表、额度测算结果超时提醒优化 |
| 二级节点 | 功能点下的可测试场景 | 新增流水记录、重复测额、大数未授权不预警、雨商/京东原逻辑保持 |
| 三级节点 | 具体测试点，必要时按正常/规则/边界/异常拆小组 | 首次测额生成流水、再次测额不覆盖旧记录、10/20/30/40/50 分钟预警 |

### 默认结构

```text
根节点：{需求标题}测试点
├── 一级功能点：{需求功能点/业务场景}
│   ├── 子功能点：{子功能/业务分支}
│   │   ├── 正常流程
│   │   │   ├── 测试点1
│   │   │   └── 测试点2
│   │   ├── 业务规则
│   │   │   └── 测试点3
│   │   ├── 边界与组合
│   │   │   └── 测试点4
│   │   └── 异常场景
│   │       └── 测试点5
│   └── 子功能点：{子功能/业务分支}
│       └── 测试点
├── 一级功能点：{需求功能点/业务场景}
│   ├── 子场景1
│   │   ├── 测试点1
│   │   └── 测试点2
│   └── 子场景2
│       └── 测试点3
└── 下游影响/关联流程（如需求明确涉及）
    └── 测试点
```

说明：

- 功能点可以继续细分子功能点/子场景；不要把过大的功能点下面直接堆一长串测试点。
- 下钻层级以“能自然挂具体测试点”为止，通常 3-4 层足够；不要为了层级整齐而空套目录。
- 每个具体功能点下不强制出现“正常流程/业务规则/边界与组合/异常场景”四个小组；没有价值就不写。
- 如果某个功能点本身已经是具体场景，可以直接把测试点放在该场景下，不必再套一层分类。
- 人工补充测试点时，应能先定位到“哪个功能点/子功能点”，再决定补到正常、规则、边界或异常。

## 叶子节点质量门禁

XMind 由 AI 生成时，必须保证叶子节点就是可执行、可验证的测试点。目录节点只负责分组，不能被叶子化。

生成 JSON 和 XMind 前必须逐节点自检：

1. 功能点、子功能点、子场景、正常流程、业务规则、边界与组合、异常场景等目录节点，必须至少包含子节点或具体测试点。
2. 叶子节点不能是纯分类词、纯名词或规则标题，例如“单客户最多5次”“调用授信接口后开始预警”“异常场景”。
3. 叶子节点应描述清楚测试条件和期望行为，优先使用“在……时/当……时/若……，验证……”这类可执行表述。
4. 如果某个目录节点下暂时没有可确认测试点，删除该目录节点，或把它展开成具体测试点；不要保留空目录。
5. 待确认规则不能生成确定性测试点；只能在测试点预览中说明“待确认后补充”。

示例：

```text
不合格叶子：单客户最多5次
合格叶子：同一客户同一次测额申请已发送5次云之家预警后，不再发送第6次预警

不合格叶子：调用授信接口后开始预警
合格叶子：大数产品已调用授信申请接口且10分钟内未返回结果时，发送第1次云之家预警

不合格叶子：异常场景
合格叶子：大数授信接口调用时间为空时，不启动大数超时预警并记录异常日志
```

## 测试设计维度

生成每个功能点下的测试点时，用以下维度做覆盖检查：

| 维度 | 关注内容 | 避免写法 |
|------|----------|----------|
| 正常流程 | 入口、触发、关键处理、落库、页面/接口/任务结果、下游影响 | 不在不同功能点重复同一入口 |
| 业务规则 | 字段来源、时间口径、状态含义、配置含义、渠道/产品差异、标识规则 | 不重复主流程描述 |
| 边界与组合 | 临界值、超期值、配置值、状态组合、渠道/产品组合、首次/多次组合 | 不重新解释规则定义 |
| 异常场景 | 缺失、非法、无记录、重复、乱序、接口失败、不满足前置条件 | 不写正常判断链路 |
| 回归影响 | 明确受影响的旧流程、旧渠道、下游结算/通知/任务 | 不单独堆低价值回归大模块 |

## 去重门禁

生成测试点前先做一次归属判断：

1. 先判断这条测试点属于哪个一级功能点，再判断是否需要落到子功能点/子场景。
2. 再判断它在该功能点下属于正常流程、业务规则、边界组合还是异常场景。
3. 同一条测试点只能出现一次。

出现冲突时优先按功能点/子功能点归属，不要因为类型相同就抽到全局大类中。

禁止生成这些割裂形态：

- 把全需求的入口都放在一个“功能流程”一级节点，导致后续找不到对应功能点。
- 把全需求的规则都放在一个“业务规则”一级节点，导致规则和业务场景分离。
- 把所有边界值集中放在一个“边界与组合场景”一级节点，导致不知道服务于哪个功能点。
- 把所有异常集中放在一个“异常场景”一级节点，导致异常和正常流程脱节。

允许的去重方式：

- 同一个功能点内，正常、规则、边界、异常之间不重复。
- 不同功能点有共同前置条件时，只在更贴近业务影响的功能点下写一次，或放到“公共前置/配置”小节点。
- 回归点贴到受影响功能点下面，不单独生成大而空的回归模块。

## 回归模块规则

默认不生成“兼容/回归范围”模块。

只有用户明确要求“回归/兼容/历史逻辑/旧流程”，或需求明确要求回归某个既有流程时，才生成少量回归测试点。

即使需要回归，也优先放在相关功能点或业务场景下，例如：

- 渠道隔离回归放入对应渠道/产品场景。
- 结算流程影响放入对应下游影响场景。
- 边界回归放入对应功能点的边界与组合小组。

不要单独堆一个低价值“兼容/回归范围”大模块。

## 测试点类型

| 类型 | 说明 |
|------|------|
| 功能 | 入口、主流程、页面/接口/任务行为、下游影响 |
| 规则 | 配置、字段、状态、渠道、产品、时间口径 |
| 边界 | 时间边界、状态边界、配置边界、组合矩阵 |
| 异常 | 缺失、失败、重复、乱序、非法值、不满足前置条件 |
| 回归 | 仅在明确需要时生成，且数量少、贴近受影响流程 |

## JSON 基本格式

```json
{
  "metadata": {
    "title": "{需求标题}_测试点",
    "created_date": "YYYY-MM-DD",
    "source_requirement": "已确认需求整理稿",
    "knowledge_base_used": false,
    "structure_policy": "feature_first"
  },
  "modules": [
    {
      "name": "测额结果流水表",
      "sub_modules": [
        {
          "name": "正常流程",
          "testpoints": ["首次测额生成一条测额结果流水", "同一客户再次测额新增历史记录且不覆盖旧记录"]
        },
        {
          "name": "边界与组合",
          "testpoints": ["同一客户多次更新测额信息时生成多条历史记录"]
        }
      ]
    }
  ]
}
```

## 输出

> **文件名前缀规则**：本环节（步骤④ 生成测试点与 XMind）产出的所有过程文件，文件名必须以所属环节步骤编号 `4-` 作为前缀，便于按七环节排序与追溯。

默认输出：

- `4-{需求名}_测试点.json`
- `4-{需求名}_测试点.xmind`

可选输出：

- `4-{需求名}_测试点生成报告.md`，仅用户明确要求“生成报告”时输出。

## 禁止项

- 需求未确认完成前禁止生成测试点。
- 默认禁止读取知识库。
- 默认禁止生成厚重报告。
- 禁止把待确认需求当成已确认规则。
- 禁止为了套模板生成低价值“兼容/回归范围”。
- 禁止把“功能流程/业务规则/边界与组合/异常场景”作为固定全局一级模块。
- 禁止让测试点脱离所属需求功能点、子功能点或业务场景。
- 禁止生成空分类节点，禁止把“正常流程/业务规则/边界与组合/异常场景/单客户最多5次”等分类或规则标题作为叶子测试点。
- XMind 必须由 `generate_xmind.py` 生成，不手写 ZIP 文件。
