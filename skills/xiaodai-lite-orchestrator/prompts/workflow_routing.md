# 七环节路由规则

## 通用门禁

1. 从 `config/step_mapping.yaml` 找到目标环节。
2. 记录 `agent_start_time`。
3. 首次需要落盘产物时，询问或确认使用者自定义输出目录，并在会话内缓存；不得固定盘符。
4. 有 `business_prompt` 的环节必须先完整读取该文件，再遵循轻量业务 Skill 的脚本和格式。
5. 校验该环节需要的输入资产；缺少关键输入时只索取缺失项，不强制重跑前序环节。
6. 交付并验证产物后记录 `agent_end_time`。
7. 有 `tracking_code` 时立即进入 `time_tracking_hooks.md`；时间记录完成前不展示下一步。
8. 无 `tracking_code` 时简要通报完成并等待新指令。

## 环节 3：确认评审

用途是把需求评审后由产品、研发或业务明确确认的模糊点、规则和边界回写到需求整理稿。

- 输入：现有需求整理稿、评审报告或待确认项、使用者给出的已确认答案。
- 只回写明确确认的内容；未确认项继续保留并标识状态。
- 不把模型推断写成确定业务规则。
- 输出新版本需求整理稿或在用户授权时更新原稿，并给出本次变更摘要。
- 不映射时间追踪步骤，不自动生成测试点。

## 环节 5：评审 XMind 测试点

用途是根据群评审或会议评审意见更新已有测试点资产。

- 小故事可以把测试点发群评审；中大故事可组织会议评审，组织方式由测试人员按需决定。
- 输入：现有测试点 JSON/XMind、评审意见和明确结论。
- 使用轻量业务 Skill 的测试点层级与叶子节点质量规则校验修改结果。
- 先更新测试点 JSON，再调用原有 XMind 生成脚本重新生成 XMind；是否覆盖原文件由使用者决定。
- 未确认意见不得擅自落入测试点。
- 不映射时间追踪步骤，不自动生成 Excel。

## 按需环节

需求评审和知识库入库只有在使用者明确提出时执行。完成前一环节时可以说明它们可选，但不得自动执行。
